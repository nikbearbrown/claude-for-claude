# Chapter 8 — Verification Is the Control System
*The agent's report is not evidence. Evidence is evidence.*

The agent returns a message: "Task complete. I've compiled the summary of the literature on treatment outcomes, organized by study design, and cross-referenced the key claims against the listed sources."

You read the summary. It is well-organized. The claims are phrased with precision. The studies sound plausible. There are parenthetical citations throughout.

You open three of the cited papers to check a claim in the conclusion. One citation does not exist. The second paper is real but says the opposite of what the summary attributes to it. The third is from a different domain entirely.

The agent was not malfunctioning. It produced a coherent artifact. What failed was not the model. What failed was the verification method — specifically, that there was none.

I want to make one argument in this chapter and make it completely: verification is not a final check you add at the end of agentic work. It is the control system that makes agentic delegation safe to act on. Designed before the agent begins. Applied after the agent finishes. Built into the plan, not appended to it.

---

## The Standard Model Is Wrong

Here is how most people think about AI-assisted work: you give the agent a task, the agent produces output, you review the output, you use it or don't. Review is the step at the end.

This model is wrong for agentic work, and the error is consequential.

Agentic systems do not just produce text. They observe data, call tools, move files, query systems, write code, and take actions whose effects persist after the session ends. An agent that has already moved files, committed code, updated records, or sent a message has changed state in the world. Reviewing the final report after those changes have occurred is not review. It is an audit of something that has already happened.

The Microsoft Research study on generative AI and critical thinking found that generative AI shifts human cognitive work toward verification, integration, and task stewardship (Microsoft Research, 2025). The question is not whether humans still have a role — the evidence is unambiguous that they do — but what that role is. For agentic tasks, the answer is this: define the evidence criteria before the agent starts, then inspect that evidence after the agent finishes. The fluent summary the agent returns is not a substitute for either step.

---

## Why the Report Isn't Evidence

Agents produce fluent summaries of their own work. "I completed the analysis." "I verified the sources." "I confirmed the counts matched." These statements are often accurate. They are also generated by the same system that did the work.

Research on hallucination in large language models establishes that high-confidence prose is not correlated with accuracy (Farquhar et al., 2024). A model can produce a confident summary of work it performed imperfectly, can misrecall a tool call it made, or can generate a plausible-sounding completion report for work that was only partially done. The fluency is the problem. The artifact does not announce its own errors — it presents them in the same register as everything else it got right.

Reflexion-style architectures allow agents to critique and revise their own outputs in response to feedback (Shinn et al., 2023). Self-critique improves output quality at the margins. It cannot serve as independent verification. An agent reviewing its own work is the same system, with the same failure modes, inspecting the same context. That is not an independent check. It is a reread.

The principle that follows is direct: for consequential outputs, independent evidence is required. Independent means collected by a method that does not rely on the same system that produced the work.

---

## What Independent Evidence Actually Looks Like

The evidence required depends on what the agent produced. There is no single verification method because there is no single artifact type.

**Code changes.** If a code assertion can be tested by execution, testing by execution is the verification method. This is a categorical principle: the HumanEval benchmark formalized it, but it precedes the benchmark — any serious engineering practice already knew it (Chen et al., 2021). Reading code and assessing whether it looks correct is not the same thing as running tests that either pass or fail. Tests, builds, lint checks, type checks — these produce external evidence. A diff review adds a second layer: what changed? Is the scope of the change consistent with what the plan stated? Are there modifications in files that should not have been touched?

**Research and claims.** An agent has access to its training data and to whatever documents were provided in context. It does not have reliable access to sources it cannot read. Even when it can read a source, it may misattribute a claim, collapse a qualification, or select a passage that misleads in isolation. Verification for research outputs means source-by-source claim checking — not skimming citations, but opening cited documents and matching the specific claim to what the document says in context. The NIST AI Risk Management Framework is explicit: output-risk management requires provenance documentation, not just output inspection (NIST, 2023; NIST, 2024).

**Data transformations.** Spreadsheet extraction, database queries, data transformation tasks — these require quantitative verification. Row counts tell you whether the agent processed the full dataset. Sample rows tell you whether individual records look right. Formula audits tell you whether calculated columns are correct. Source maps tell you which output came from which input. An agent that processed 247 rows when the source had 312 without flagging the discrepancy has produced an incomplete output that does not announce itself as incomplete. That is the failure mode to prevent.

**File operations.** When an agent moves, renames, creates, or deletes files, the verification method is a before-and-after inventory. Take a snapshot of the relevant folder before the agent acts. Compare it to the snapshot after. Every change is now visible; anything unexpected becomes identifiable. Anthropic's guidance on using Cowork safely recommends exactly this posture for file-affecting workflows (Anthropic, 2025) [verify — current as of writing].

**Visual outputs.** A chart may look clean while the axes are mislabeled, the scale is inverted, the data is sampled incorrectly, or the caption attributes findings the data does not support. Research on chart misinformation shows that misleading charts often function through framing and captioning rather than visual tricks alone (CHI, 2023). The verification method for a chart is: trace every claim in the caption to the underlying data and confirm that axis labels, scale, and units are correct. Cleveland and McGill's foundational work on graphical perception established that viewers systematically misread certain chart types (1984). An agent does not know which chart type will mislead a given reader. That judgment belongs to the human.

**External actions.** Any action that crosses a boundary out of the system — sending an email, posting to a platform, submitting a form, calling an external API — requires human final approval before it happens. Not after. Before. Once a message is sent, it is sent. This is not a verification method in the same sense as the others; it is a structural gate that precedes action rather than following it.

## Building Verification Into the Plan

Every plan should end with a specific answer to the question: how will we know the task is complete?

If the agent cannot name an evidence method, or if the method it names amounts to "I'll confirm when I'm done," the plan is not ready to approve. A simple prompt addition enforces this: *"Before acting, tell me what evidence will show the task is complete. If there is no reliable verification path for this task, stop and ask me."*

That instruction does two things. It tells the agent to produce an evidence statement before execution. It also gives the agent explicit permission to stop — which matters, because agents without explicit stop conditions often proceed anyway and produce confident summaries of work they should not have attempted.

The ReAct loop shows how observations from actions feed back into reasoning (Yao et al., 2023). Verification is the human-supervised version of this: after each significant action, the human checks the observations rather than accepting the agent's summary of them.

## Four Methods, Four Levels of Independence

Self-check, second-model review, automated testing, and human verification are sometimes treated as interchangeable. They are not, and understanding why matters for knowing when each is adequate.

**Self-check** is the agent reviewing its own output. It catches surface contradictions. It cannot catch systematic errors that affected the original work, cannot access sources the model lacks, and shares the same failure modes as the original generation. Useful for obvious errors. Not evidence for consequential outputs.

**Second-model review** passes the output to a different model instance or a differently prompted model for review. This adds some diversity of perspective, but both models share the same training distribution and the same hallucination failure modes. A second model saying "this looks correct" is weak evidence. Not nothing, but not independence.

**Automated testing** is the strongest verification form for code and data tasks because execution does not defer to confidence. A test suite that passes is evidence. A build that fails is evidence. These are external to the model's reasoning and catch errors the model cannot see in its own output. The limitation is that automated tests can only check what they were written to check — they will not catch a logic error in untested branches or a data quality problem in unsampled rows.

**Human or source verification** means a person opens the cited document, runs the independent calculation, checks the diff against the stated scope, or reads the output with domain knowledge. This is the gold standard for consequential outputs. It is also the most expensive. The right design is to keep agent scope narrow enough that strict human verification is rarely required — not to replace it with a weaker method when the stakes demand it.

## A Worked Trace: Literature Summary

A researcher asks an agent to summarize the literature on a specific treatment protocol, citing the key studies and their findings.

*Before the agent starts:* The researcher adds to the task: "Before acting, tell me how you'll verify the summary is accurate. I need to know which documents you'll read, and at the end I need a source map showing which claim comes from which document."

*Agent plan response:* "I will read the six documents in the /research/treatment-protocol/ folder. I will not cite studies I cannot open in the current context. My evidence will be: a source map pairing each claim in the summary with the document and page or section it comes from. If I encounter any claim I cannot trace to an opened document, I will flag it explicitly."

*The researcher approves this plan.*

*After the agent finishes:* The researcher receives the summary with a source map. She does not read the whole summary first. She picks five claims from the source map, opens those documents, and checks whether each claim matches what the document says in context.

Two match precisely. Two are slight oversimplifications she notes in her edits. One misattributes a qualification to the wrong study. She corrects the misattribution and notes the simplifications for context in her final document.

The process worked not because the agent was perfect, but because the verification method was specific enough to find errors that mattered.

## When to Reject a Task

Some tasks do not have a reliable verification path. There are signals:

The agent's output cannot be traced to specific sources or data — pure synthesis tasks where no citation trail is possible. The tools required to verify the output are not available to the human. The task requires domain expertise the human does not have and no expert reviewer is in the loop. The task involves external-facing action that cannot be reviewed before it happens.

When these conditions apply and the stakes are high, the right response is to revise the task, not to proceed without a verification path. A narrower task with a reliable evidence method is more useful than a broader task that produces an artifact the human cannot inspect.

This is not timidity. It is the discipline that makes agentic work trustworthy rather than merely impressive.

---

## Verification Tiering

Like the access ladder in Chapter 3, verification should be risk-tiered.

*Light verification* applies to low-risk, reversible, narrow tasks: a draft for internal use only, a summary for working purposes, a file organization proposal not yet executed. Light verification means reading the output critically and confirming it is consistent with the inputs provided.

*Standard verification* applies to tasks with persistent outputs, write access, or external use: a report going to stakeholders, a code change going to a branch, a data extraction feeding a downstream tool. Standard verification means working through the evidence matrix for the relevant output type.

*Strict verification* applies to high-risk, irreversible, or regulated workflows: production code changes, client-facing materials, financial records, health or safety information, external communications. Strict verification means the full evidence method plus a second reviewer — human or domain expert — before the output is transmitted.

The NIST AI RMF Generative AI Profile supports this tiering: outputs should be evaluated relative to their risk profile, with human oversight proportional to consequence (NIST, 2024).

---

## The Approval Gate Before Use

The final gate is the moment before the output is used, transmitted, or acted on. At that gate the human should be able to answer four questions:

What evidence method was applied to this output? Did the evidence check pass, partially pass, or identify errors? Were any errors corrected, and is the correction documented? Is there any claim or element in this output that could not be verified?

If the answer to the last question is yes and the output is going somewhere consequential, that limitation should be stated explicitly wherever the output goes. That is intellectual honesty. It is also the human accountability that no agent can substitute for — and that no fluent summary can perform on the agent's behalf.

## What Would Change My Mind

The emphasis on pre-specified, artifact-matched, human-inspected evidence would relax under a few conditions. If automated verification tools became reliable enough across code, research, and data tasks that the human's role shifted to setting verification criteria rather than executing verification steps, the burden would shift upstream rather than disappear. If second-model review were shown empirically to detect the same errors that independent human review detects, at comparable rates, it would deserve more weight than it currently gets. If agentic runtimes developed persistent, inspectable action logs that let humans trace every tool call and data read without relying on the agent's self-report, the report stage would matter less.

Some of these conditions are developing [verify — current as of writing]. None are mature enough to reduce the verification burden for high-stakes tasks today.

## Still Puzzling

How should verification scale when the agentic task is itself the generation of thousands of records, summaries, or code files — too many for human review of each item? Sampling is the obvious answer, but the right sampling strategy is not obvious, and the errors most likely to matter may not be randomly distributed across the population.

What is the right model for verification when the human lacks domain expertise and there is no expert reviewer in the loop? This is not an edge case; it is a common situation wherever AI is deployed to accelerate work at the boundary of the user's knowledge. The verification framework I've described assumes the human can evaluate the evidence. When they can't, the framework is incomplete.

## LLM Exercises

**1.** Take a task you have previously completed with an AI assistant — a summary, a code change, a data extraction, a research synthesis. Identify the output type. Using the evidence matrix, specify what verification you should have applied to each element. Compare what you actually did to what the matrix recommends. Now ask Claude to audit the same output using the specific evidence method the matrix calls for. What does Claude's audit find that your review missed, or vice versa?

**2.** Write a task packet for an agentic task you want to delegate, ending with the line: "Before acting, tell me what evidence will show the task is complete. If there is no reliable verification path for this task, stop and ask me." Submit the packet to Claude. Evaluate whether the evidence statement it proposes is genuinely independent of the agent's own report, or whether it amounts to self-certification. Revise the packet to close any gap you find.

**3.** Choose a task that, on reflection, you believe should be rejected under the no-reliable-verification-path rule. Argue both sides: first, why the task should be rejected; second, what changes to scope, tool access, or review structure would make the task verifiable. Which version of the task would you actually delegate, and under what conditions?
